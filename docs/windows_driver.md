# Разбор Windows-драйвера Goodix

Источник: `vendor/windows/FingerPrint_1.1.141.36.zip`
(sha256 `74052a274239e17ac8fa95314e22d8db1770a3b9df28c90c9a9178231418f435`).
Распаковка: zip → zip → NSIS → NSIS. **Ничего не запускалось**, только разбор архивов.

## Что внутри

| Файл | Что это |
|---|---|
| `gfspi.inf` | INF: `ACPI\GXFP51A7`, `ACPI\GXFP51A0` — **SPI**-вариант, не USB |
| `gfspi.dll` | UMDF-драйвер, 3.5 МБ; здесь конфиги сенсоров и mbedtls |
| `WBDI_Enclave.signed.dll` | SGX-энклав: `tls_enclave.c`, `dh_enclave.c`, `gf_chicagohs.cpp` |
| `Engine_Enclave_3.0x.xx.signed.dll` | SGX-энклав сопоставления, `Milan_v_3.02.00.15` |
| `EngineAdapter.dll` | WinBio engine adapter |

Пути сборки внутри: `winfpcode\Milan_Watt\MilanSpi\...` — платформа **Milan**, та же,
что у семейства в `vendor/goodix-fp-dump`. В `gfspi.dll` есть строки
`GF_ST411SEC_APP_14114` и `GF_HC460SEC_APP_141xx` — **тот же кристалл ST411SEC**,
что и у нашего `GF_ST411SEC_APP_12705`, только другая ветка прошивки.

SGX-энклавы на диске не зашифрованы (шифруется только их память в рантайме),
поэтому строки и константы из них читаются.

## TLS

Стек — **mbedtls**. Наборы шифров: `TLS-PSK-WITH-AES-128-GCM-SHA256` (ровно тот,
что предлагает наше устройство) и `TLS-PSK-WITH-AES-128-CBC-SHA256`.
Идентификатор — `Client_identity`.

**Известного white box семейства (`ec35ae3a…`) в пакете НЕТ** — здесь другая схема ключа.

Кандидат на PSK: в блоке строк лежит `123456` ровно в позиции `DFL_PSK` из
mbedtls-сэмпла `ssl_client2.c` — порядок строк
`localhost` → `4433` → `/` → **`123456`** → `Client_identity`
в точности повторяет порядок дефайнов в сэмпле. В сэмпле PSK задаётся hex-строкой
и разбирается через unhexify, поэтому проверять надо оба варианта.

Ещё одна 16-байтовая hex-константа — `f772d408fa1a4e72ab957b66c0785c3a`, но лежит
в блоке UMDF-трассировки, похоже на GUID провайдера, а не на ключ.

## DEVICE_CONFIG

В `gfspi.dll` найдено **5 блобов по 256 байт** по сигнатуре `?11 60 71`
(смещения в `docs/configs_gfspi.json`):

| Смещение | Байт 0 | Комментарий |
|---|---|---|
| `0x35a4d0` | `0x28` | |
| `0x35a5d0` | `0x38` | |
| `0x35aed0` | `0x60` | совпадает по началу с `DEVICE_CONFIG` из `driver_55x4.py` |
| `0x35afd0` | `0x70` | **почти точная копия `DEVICE_CONFIG` из `driver_51x7.py`** |
| `0x35b0d0` | `0x58` | отличается от предыдущего только байтом 0 |

Блоб `0x35afd0` отличается от конфига в `driver_51x7.py` всего пятью байтами:
`0x087: 04→24`, `0x0c8: 1b→15`, `0x0eb: 10→00` и два байта контрольной суммы
(`0x0fe..0x0ff: 8d1e→bcff`). То есть формат тот же, отличается тонкая настройка.

Байт 0 (`0x28/0x38/0x58/0x60/0x70`) кодирует вариант сенсора: у `driver_51x7` он
`0x70`, у `driver_55x4` — `0x60`.

Проверка этих конфигов на живом устройстве — `tools/try_configs.py`.


## Итог разбора (проверено на живом устройстве)

**Этот пакет нам не подходит напрямую — но не бесполезен.**

- **DEVICE_CONFIG:** все 5 блобов устройство ОТВЕРГАЕТ (`UPLOAD_CONFIG_MCU` ->
  ответ `90 03 00 00`, первый байт payload `0x00` = отказ; у верного был бы `0x01`).
  Прошивка активно валидирует блоб. Причина: пакет для ветки `141xx`/SPI-кристалла,
  а у нас USB `GF_ST411SEC_APP_12705`. Формат совпадает, значения — нет.
- **PSK:** 6 кандидатов из бинарника (`123456` из mbedtls-сэмпла в обоих видах,
  hex-константа, sha256 и т.д.) — ни один не поднял TLS. `123456` — это `DFL_PSK`,
  дефолтная заглушка сэмпла `ssl_client2.c`, а не рабочий ключ.
- **Почему ключа нет в открытом виде:** реальный PSK живёт внутри SGX-энклава
  `WBDI_Enclave.signed.dll` (`tls_enclave.c`). Энклав на диске зашифрован и
  раскрывается только на CPU с ключами конкретной машины — статически его не достать.

**Вывод:** нужен либо USB-пакет драйвера именно для нашей модели (ветка 127xx), либо
динамический дамп (энклав в рантайме, или USB-трафик с рабочего Windows). Оба требуют
запущенного Windows, которого нет. Оставшийся реалистичный путь к работе устройства —
перезапись PSK своим ключом (PRESET_PSK_WRITE), а конфиг тогда придётся подбирать/править.

## Итог: путь определён

Штатный community-флоу (goodix-fp-dump driver_51x7) для устройства с вендорским PSK —
**стереть прошивку + вписать свой white box + перепрошить** (erase_firmware -> write_psk
-> update_firmware). Это разрушительно, требует прошивку под наш чип и запрещено guard'ом.

**Безопасный путь: извлечь настоящий вендорский PSK из gfusb.dll** (энклавов нет, ключ
обязан быть в бинаре) — тогда TLS откроется без единой записи в устройство. Это цель
следующего этапа и основная оставшаяся работа (статический реверс x64-кода настройки TLS).

## РЕВЕРС gfusb.dll (Ghidra headless) — где на самом деле PSK

Реконструирована схема PSK (функции gf_production.c / tls_lib.c / seccipher.c):

1. `tlslib_server_init` (FUN_18005ed7c): PSK приходит **аргументом** и уходит в
   `mbedtls_ssl_conf_psk(conf, psk, psk_len, "Client_identity")`. В самом init ключа нет.
2. `production_get_host_psk_data` (FUN_18003ff08): источник PSK. Порядок:
   - читает хостовый кэш `Goodix_Cache.bin`, иначе
   - читает **sealed-блоб из MCU** командой `production_read_specific_data(0xbb010002)`
     (это ЧТЕНИЕ, безопасно), последние 8 байт блоба — случайный seed;
   - `generate_entropy2` (FUN_18003f544): выводит 0x30-байтовую entropy из
     **seed + SHA256 + 3 вшитых констант**:
       - `DAT_1802a3df0 = 9d7992b38402b66c81d1f555218942a9`
       - `DAT_1802a3e00 = 1848d71550d270d219c80632ab4f8bb3`
       - `DAT_1802a3e10 = e47c8938db5250f0205617ee17da4eb4`
   - `FUN_18000d604` распечатывает блоб.
3. **`FUN_18000d604` = Windows `CryptUnprotectData` (DPAPI)**, а entropy из п.2 —
   лишь `pOptionalEntropy` (вторичная соль). Seal-парная `FUN_18000d2f8` =
   `CryptProtectData` с флагом `4 = CRYPTPROTECT_LOCAL_MACHINE`.
   Хеш везде — `SecSha256` (FUN_1800072d0), рандом — CryptGenRandom (FUN_18000cf98).

### Приговор варианту A
PSK — это **случайные 32 байта, сгенерированные хостом при провижининге и запечатанные
Windows DPAPI (LOCAL_MACHINE)**. В драйвере ключа НЕТ — только DPAPI-соль (константы выше).
Распечатать sealed-блоб устройства можно **только на той установке Windows**, что его
запечатала (мастер-ключ DPAPI в `Windows\System32\Microsoft\Protect\S-1-5-18`).

На диске ноутбука — только Linux (ext4 + EFI), NTFS/Windows/DPAPI нет. Исходный Windows,
провижинивший сенсор, стёрт. **Значит заводской PSK невосстановим, и вариант A
(достать PSK из драйвера) не даёт рабочего ключа. Тупик подтверждён реверсом.**

Важное следствие: заводской ключ УЖЕ фактически потерян (нечем распечатать). Поэтому
перезапись PSK (вариант B) больше ничего ценного не разрушает — прежний довод «потеряешь
заводской ключ» отпал.

## Как драйвер СОЗДАЁТ ключ (production_write_key, FUN_180041478)

Реверс показал, что делает Windows, когда валидного PSK нет (наш случай):

1. `production_psk_process` (FUN_1800407e8): проверить PSK (`production_check_psk_is_valid`).
   Невалиден -> вызвать `production_write_key`.
2. `production_write_key` (FUN_180041478):
   - `generate_entropy2` (константы + random seed);
   - **генерит СЛУЧАЙНЫЕ 32 байта PSK** (CryptGenRandom);
   - DPAPI-запечатывает копию (TLV `0xbb010002`) — хостовое хранилище;
   - **оборачивает PSK в «белый ящик»** `FUN_180006bb0` и пишет как TLV **`0xbb010003`** —
     это то, что устройство реально использует для TLS.

Т.е. Windows не «достаёт» ключ ниоткуда — при первом запуске он **чеканит новый случайный
ключ и записывает его в устройство**. Именно поэтому хеш нашего устройства уникален
(`4d87fa…`), а не семейный.

### Белый ящик (FUN_180006bb0) — что это
Строит конверт: заголовок `0xff02` + длина + SHA + симметричный шифр 16-байтовыми блоками
(FUN_1800056a0, счётчик в ctx+0x220 = CTR-подобный режим) с ключом из key-schedule
(FUN_180003040). Это **кастомный симметричный white-box**, НЕ чистый RSA. Завязан на
вшитые константы/ключи (DAT_1802cfe00/e38 и др.). Воспроизвести можно в принципе (ключи в
бинаре), но white-box специально устроен так, чтобы это было трудно — это отдельная большая
работа с неясной гарантией.

### Вывод (уточняет прежний «тупик»)
- Заводской (старый) ключ невосстановим — DPAPI, Windows стёрт. Это остаётся верным.
- НО «сделать рабочим» = **отчеканить НОВЫЙ ключ и записать белым ящиком** — ровно то, что
  делает Windows. Это воспроизводимо. Два пути:
  (A) Реверснуть white-box до конца и чеканить ключ на Linux (без Windows). Трудоёмко.
  (B) Дать это сделать официальному драйверу в Windows-VM с проброшенным USB, а ключ и
      конфиг СНЯТЬ (из нашей же VM + USB-дамп) и проиграть на Linux. Ниже риск, короче путь.

## ПРОРЫВ: white-box воспроизведён эмуляцией (путь A работает)

`FUN_180006bb0` (обёртка PSK в white-box) выполнена под Unicorn (tools/emu/emu_whitebox.py):
образ gfusb.dll мапится по 0x180000000, застаблены Win32-heap/cookie/CFG, вызов
`FUN_180006bb0(psk, 0x20, out, &len)`.

- Функция **детерминирована** (в дереве нет CryptGenRandom): один PSK -> одна константа.
- Проверено: psk=0 даёт идентичный результат дважды; разные psk -> разные white-box; ret=0.
- **white-box для PSK=0 (102 байта) сохранён в docs/whitebox_psk0.hex.**
  Структура: [32-байт внешняя подпись][02 ff][len=20 00 00 00][16-байт nonce][шифртекст+тег].
- Ключ обёртки — общесемейный, вшит в gfusb.dll -> одна константа годится для ВСЕХ 5f10.
  Это и делает драйвер распространяемым без Windows.

### Команда записи
`production_write_key` -> `FUN_180041e18` -> `FUN_1800630d4(..., 0xe, 0, ...)` =
категория 0xE, команда 0 = байт **0xe0 = PRESET_PSK_WRITE** (classic-фрейминг).
То же, что `preset_psk_write` в goodix-fp-dump. driver_51x7 (та же ST411-линейка!) штатно
делает `preset_psk_write(0xbb010003, PSK_WHITE_BOX)` и дальше TLS с нулевым psk — наш план
идентичен, только white-box наш (под ключ 127xx).

### План провижининга на Linux (без Windows) — ТРЕБУЕТ записи во флеш
1. baseline: preset_psk_read(0xbb020003) = 4d87fad3…(текущий заводской хеш, уже мёртв).
2. preset_psk_write(0xbb010003, whitebox_psk0)  <-- флеш-запись, guard блокирует, нужно "да".
3. preset_psk_read(0xbb020003) -> ждём смену хеша.
4. TLS-PSK хендшейк с psk=0 (openssl s_server -psk 00..) -> успех = psk=0 принят.

Риск записи: 0xe0 пишет СЛОТ PSK, это НЕ стирание прошивки (0xa4). Худшее реалистичное —
неверный white-box, тогда просто перезапишем другой. Заводской ключ и так потерян.

## Первая попытка записи — ОТКЛОНЕНА (код 3), устройство цело

Записали `preset_psk_write(0xbb010003, whitebox_psk0)` (classic 0xe0, флаг верный, len 102):
- устройство ACK'нуло команду, затем ответило `e0 … 03` -> **код возврата 3 = отклонено валидацией**;
- после этого `preset_psk_read(0xbb020003)` стал возвращать ошибку 1 (psk-подсистема
  заблокировалась — в прошивке есть счётчики «check psk times»/«write psk times»,
  живут в volatile-памяти MCU: soft-reset и reset(0xa2) НЕ снимают, нужен полный power-cycle/ребут);
- прошивка и reset работают -> **устройство НЕ повреждено**, слот PSK, судя по коду 3, не изменён.

Проверенные гипотезы:
- `DAT_1802cfe00` (ветка в обёртке) в коде никогда не пишется -> всегда 0 -> эмуляция шла
  верной веткой, white-box посчитан для правильных условий. НЕ причина.

Оставшиеся версии причины кода 3 (проверять реверсом ДО следующей попытки, т.к. счётчик
попыток ограничен):
1. Устройству нужен ПОЛНЫЙ production-blob, а не одиночный TLV: драйвер шлёт
   `[0xbb010002 sealed][seed(8)][0xbb010003 wb]` одним 0xe0 (FUN_180041e18), мы послали только
   0xbb010003. (goodix-fp-dump 51xx шлёт одиночный и ему хватает — у 127xx может быть иначе.)
2. Устройство не перезаписывает уже валидный заводской PSK без предварительного шага
   (production-session / erase). Тогда «мягкий путь» на running-firmware не проходит.
3. Есть подготовительная команда (вход в production-режим) перед записью.

ВАЖНО: не долбить устройство вслепую — psk-счётчик может залочиться насовсем.
Сначала реверс точного формата/предусловия, потом одна выверенная попытка.

## РЕШЕНО: провижининг на Linux работает (2026-08-22)

Записали полный production-blob и устройство ПРИНЯЛО:
- `preset_psk_write` 0xe0 с blob `[0xbb010002: sealed(32)+seed(8)][0xbb010003: white-box(102)]` -> OK;
- PMK hash сменился на a9bc686ead9594b39bc7cbe6c935c228894d08abd82aea5c03de81235753f83c;
- TLS-PSK хендшейк с нашим psk (docs/psk.hex) -> ChangeCipherSpec = **принят**.

Ключевые выводы:
1. Устройству нужен ПОЛНЫЙ blob, а не одиночный TLV 0xbb010003 (в этом была причина кода 3).
2. sealed-часть (0xbb010002) для НАС может быть dummy (32 байта 0xd1) — устройство хранит её
   непрозрачно; мы psk используем напрямую, DPAPI не нужен.
3. white-box детерминирован от psk на вшитом семейном ключе -> одна пара (psk, blob) годится
   для ВСЕХ 27c6:5f10. Полностью распространяемо, без Windows.
