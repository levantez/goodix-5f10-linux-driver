# Калибровка кадра — текущий блокер

## Симптом
Полный конвейер работает: provision → config accepted → TLS → FDT → `mcu_get_image` →
устройство отдаёт зашифрованный кадр (~14.8 КБ TLS app-data) → openssl расшифровывает.
НО расшифрованный кадр — **практически все нули** (пиксели пустые). Палец меняет
несколько байт (FDT-детекция жива), но пиксельные данные не формируются.

## Что установлено реверсом
- Наш чип: **ChicagoHU**, id `a4082200`, reset number **1024** (у 51x7 — `a2042500`/2048).
  Это НОВЫЙ вариант линейки GF_ST411SEC (fw 12705), не покрытый goodix-fp-dump.
- DAC/gain берутся из OTP: `FUN_18002be00` вызывает `ChicagoHU_OTP_DAC_Check`
  (`FUN_18002a2a8`), которая читает DAC из OTP-структуры на смещениях **0x2e–0x35**
  и пишет в регистры **0x220 (=dac0<<4|8), 0x236, 0x238, 0x23a**.
- OTP-структура в драйвере — **64 байта** (`FUN_180029ca0` читает до 0x3f), но команда
  `READ_OTP (0xa6)` отдаёт только **32 байта** при любом payload. Полный 64-байтный OTP
  читается иначе (не нашли точную команду; `OnProductionProcess`/production-data — хостовый
  обработчик, не путь чтения OTP из MCU).

## Что проверено эмпирически
- Свип регистра `0x220` (весь диапазон старшего байта 00..1c, младший 00/78/f0):
  кадр остаётся пустым (0 ненулевых). Значит **один DAC 0x220 картинку не оживляет** —
  проблема шире: либо нужны все 4 DAC + правильный конфиг под ChicagoHU, либо
  последовательность захвата (FDT/mcu_get_image) для нашего чипа отличается от 51x7.

## Почему это трудно
Настоящий конфиг строится в рантайме (`ChicagoHU_check_and_parse_otp` →
`modify_sensor_config` → download `FUN_180016d80`) в многопоточной машине состояний,
завязанной на глобальный контекст `DAT_1802ad898`. Холодная эмуляция дорога; полный
реверс OTP-чтения + DAC-математики + построителя конфига — многосессионная работа.

## Возможные пути (следующие шаги)
1. Найти точную команду чтения 64-байтного OTP (реверс инициализации, где вызывается
   `check_and_parse_otp` с 64-байтным буфером) → прочитать полный OTP → извлечь DAC
   0x2e–0x35 → применить все 4 регистра.
2. Либо эмулировать `FUN_18002be00` на нашем 32-байтном OTP, если распаковка идёт из 32→64
   (проверить, действительно ли `FUN_180029ca0` разворачивает 32 байта; в декомпиляции она
   читает param_1+0x24..0x3f как байты — т.е. ждёт уже 64 байта на входе).
3. Либо снять реальный init/config через Windows-USB-дамп (пользователь исключил).

## Вывод
Калиброванный кадр — реальный, нетривиальный блокер для нового чипа a4082200.
Провижининг и весь транспорт готовы; картинка требует отдельного захода по реверсу OTP/конфига.

## ПРОРЫВ (2026-08-22): наш чип = milanG, не 51x7/ChicagoHU

Диспетчер FUN_18006a22c выбирает парсер OTP по chip-id:
- 0x2205 -> milanL ; **0x2208 -> FUN_180036030 = milanG (НАШ, sensorType 2, cols 0x20)** ;
  0x2503/4 -> ChicagoHU ; 0x2507/8/0x2510 -> ChicagoT.
Наш chip id (read_sensor_register 0,4 = a4082200) => **0x2208 => milanG**.

milanG_check_and_parse_otp (FUN_180036030) ВЫЧИСЛЯЕТ DAC из наших же 32 байт OTP:
- dacvalue из otp[0x1a]/otp[0x1f]/~otp[0x1b] (у нас все = 0x36)
- second из otp[0x16]/otp[0x19]/~otp[0x17] (у нас все = 0xf9)
Наш OTP: ea468666 d4501cfc 30af0071 02044674 2e20a269 0100f906 9ef936c9 c09d3436
=> DAC-РЕГИСТРЫ (через modify_sensor_config, патч конфига):
  reg 0x220 = dacvalue<<4 | 8         = 0x36<<4|8 = **0x0368**
  reg 0x5c  = ((second>>4)+1)*0x10    = (0xf+1)*0x10 = **0x0100**
  reg 0x5e  = ((second&0xf)+2)*0x6400 / reg0x5c = (11*0x6400)/0x100 = **0x044c**
Регистры 0x236/0x238/0x23a (из 51x7) НАМ НЕ НУЖНЫ — это другой чип.

СЛЕДСТВИЕ: мы грузили ЧУЖОЙ конфиг (51x7) и чужой DAC -> пустой кадр.
Нужен milanG-конфиг (sensorType 2, cols 0x20) + патч DAC выше.
